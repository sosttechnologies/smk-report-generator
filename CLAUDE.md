# SMK Gateway — Termly Report Generator

Internal staff tool for **SIEVEMK / SMK Gateway**, a UK education charity in Milton Keynes
(company 7886477, registered charity 1146451) providing tutoring to students aged 11+.

Tutors submit a **weekly** Microsoft Form per student, per subject. Staff currently retype
those responses by hand into a ~6-page "Interim Termly Report". This tool reads the
submissions, drafts every section, lets staff edit, and exports the letterhead PDF.

## Three hard rules

1. **Nothing exports without a human clicking Approve.** These are reports about children,
   read by their families. The `approved` state gates export; "Edit again" clears it.
2. **A half-filled form still produces a report.** Only the student's name is required.
   Every other blank — subject, week, attendance, ratings, comments — gets a *stated*
   default (`General`, the submission date or current week, "not recorded") that is listed
   in the file preview, and the document says what was not recorded rather than inventing a
   grade or a sentence. Never skip a row, and never guess an attendance or a rating.
3. **No real student data in this repository.** Everything in `sample-data/` is invented.
   Never commit a real SIEVEMK Forms export, PDF or screenshot containing a real child's
   name, comments or circumstances. The UK GDPR position on sending children's data to an
   LLM has **not** been settled with SIEVEMK — that must happen before this handles real data.

## How it is put together

One UI, two ways of hosting it.

| Path | What it is |
|---|---|
| `artifact2/` | **The UI, and all the report logic.** A static page: `index.html`, `app.js`, `engine.js`, `runtime.js`. The single source. |
| `src/` | **The backend.** Next.js serves the UI at `/app`, gates it behind sign-in, and provides `/api/llm`, `/api/pdf`, `/api/state`, `/api/reports/[id]`, `/api/settings`, `/api/health`. Keys live here. |
| `public/app/` | Generated by `scripts/sync-app.sh` from `artifact2/` on every dev and build. Gitignored. |
| `prisma/` | Schema and migrations for the hosted app's storage. |
| `artifact/` | The first design. **Dead — delete it.** |

`artifact2/runtime.js` is the seam. Inside claude.ai it hands `app.js` the host's `sample`
and `downloads`; served by our backend it provides the same four calls over `fetch` to
`/api/llm` and `/api/pdf`. **`app.js` must never know which it is running on.**

`artifact2/engine.js` holds the parsing, aggregation, derived ratings and pseudonymisation.
**It is what actually runs.** `src/lib/{parse,parseWeekly,aggregate,report,formSchema,
pseudonymise,ingest/,generate/}.ts` is a duplicate of it that nothing reachable imports —
see "Known problems" below before touching either.

### Where work is kept
`runtime.js` also chooses the store: `localStorage` in the artifact, the organisation's
database when signed in to our server. `app.js` calls `store.load()` once at boot and
`save()` after every change; `save()` compares each report against the version the store
last confirmed and flushes what differs (debounced 800ms for the network, immediate for
localStorage). A 409 means someone else saved first — the UI reloads that report and says
so. Which folders are open stays local to each person even when signed in.

### Which model
Chosen by `LLM_PROVIDER` on the server: `anthropic`, `openrouter` (any model it lists,
open-weight included — one key), `openai`, `ollama` (inside SMK's own network), or `none`.
With `none` the app still works end to end on the deterministic template. See `.env.example`.
No vendor or model is ever named in the UI.

## Running it

```bash
npm run db          # local Postgres (Prisma's own dev server — no Docker). Prints DATABASE_URL.
npm run db:migrate  # apply migrations to it
npm run dev         # http://localhost:3000
npm run sample      # regenerate sample-data/smk-progress-forms-spring-2026.xlsx
npm run build
npm test            # 292 browser assertions against artifact2/ served statically
npm run test:web    # the self-hosted app: template path, then a fake model server (24)
npm run test:hosted # sign-in, the closed door, storage (28). Needs DATABASE_URL.
```

**To open it locally without signing in**, set `AUTH_DISABLED=true` — it is honoured only
for requests that genuinely arrived at localhost (`src/lib/authMode.ts`), so it cannot
open a deployment, and `/api/health` turns red while it is set.

**To sign in locally**, leave auth on and set `ALLOWED_EMAILS`. With no `RESEND_API_KEY`
the sign-in link is printed to the server log instead of emailed — grep the dev output for
`[sign-in]`.

`npm test` drives a real Chromium through the whole app. It is the gate — run it before any
publish. Suites live in `tests/`; `node tests/run.mjs 03` runs one.

Copy `.env.example` to `.env.local` and set a key for model drafting (see "Which model").
Without one the app still works end to end: SMK's own Word and PDF reports are read by
matching their fixed layout, and generation falls back to a deterministic template. Only
**images** and documents in some *other* layout need a model.

## Deployment

The key belongs in **server** environment variables, never in client code. Use SIEVEMK's own
Anthropic organisation key — the commercial API is covered by Anthropic's DPA and is not
trained on, which consumer claude.ai usage does not guarantee.

PDF export runs Puppeteer, so this needs a host that runs a real process with Chromium
available: **Railway, Render or Fly.io**, via the included `Dockerfile`. Vercel's default
serverless runtime will not run it without swapping in `@sparticuz/chromium`.

`scripts/deploy.sh` deploys to Fly and is idempotent — it creates the app, database and
secrets if they are missing and otherwise just ships. Run it as:

```bash
export PATH="$HOME/.fly/bin:$PATH"
export ALLOWED_EMAILS="someone@example.org"   # required; an empty list admits nobody
./scripts/deploy.sh
```

It refuses to run without `fly auth login` (a browser flow). London (`lhr`) is chosen so
children's records stay in the UK. The Dockerfile generates the Prisma client at build and
runs `prisma migrate deploy` on boot, so a release and the schema it expects ship together.

**Moving to a custom domain** is `fly certs add <host>`, a CNAME, and changing the
`AUTH_URL` and `APP_URL` secrets. No code references the hostname.

**Read the Spending section before running the script** — it provisions a database.

The page published as a claude.ai Artifact (`artifact/`) is a **demo only**. It is
client-side, so it can never hold an API key; it borrows the viewer's own Claude through the
`sample` runtime capability. Never put a key in it.

## Data protection

`src/lib/pseudonymise.ts` is a hard boundary: **no student or tutor name reaches the model.**
Before a generation request leaves the server, names are replaced with `Student A` / `Tutor 1`
tokens (including inside free-text comments and record ids); the model's answer is rehydrated
here. `npm run check:privacy` asserts no name leaks and fails the run if one does — keep it
passing.

`findResidualRisks()` flags what the name swap cannot catch — addresses, postcodes, phone
numbers, family mentions, health and SEND language — for staff to redact before sending.

Three things to keep stating plainly rather than burying:
- Pseudonymisation is **not** anonymisation. Pseudonymised data is still personal data under
  UK GDPR; this demonstrates data minimisation, it does not remove any obligation.
- The SOCIAL, EMOTIONAL AND MENTAL HEALTH and SENSORY/PHYSICAL sections attract **Article 9
  special category** health data. Tokens do not change that.
- Free-text scrubbing is imperfect. The only reliable control is what tutors are told to
  write in the Microsoft Form.

## Pushing

Commits reach GitHub automatically: a Stop hook in `.claude/settings.local.json` runs
`scripts/auto-push.sh` after each turn, which pushes anything local that the remote does not
have. It never creates commits — an auto-generated message is worse than none, and committing
blindly would ship half-finished work — so it reports uncommitted files instead of hiding them.
It always exits 0; a failed push cannot block a turn.

`settings.local.json` is gitignored, so this is personal. A teammate cloning the repo does not
inherit auto-push.

Repo: `sosttechnologies/smk-report-generator`, **private**. It holds SMK's letterhead details
and screenshots of their internal report format — keep it private.

## Shape of the thing

**Input** — one row per student × subject × week, from a 10-question form:
student name, instructor name, subject, week beginning, weekly attendance, a
STUDENT ENGAGEMENT grid, an ACADEMICS grid, concerns, key actions, general comments.
See `.claude/skills/smk-form-schema/SKILL.md`.

App shell, tokens and state model: `.claude/skills/smk-app-design/SKILL.md`.

**Output** — one report per student per term: an overview page, an 8-column subject matrix,
then eight label/body sections. See `.claude/skills/smk-report-format/SKILL.md`.

Three ingestion paths (browser: `readSpreadsheet` / `extractDoc` in `artifact2/app.js`;
server twins in `src/lib/`):

| Upload | Path | Notes |
|---|---|---|
| `.xlsx` `.csv` | `parse.ts` / `engine.js rowsToSubmissions` | Deterministic. Fuzzy header matching, no model. |
| `.pdf` `.docx` `.txt` in SMK's layouts | `parseWeekly.ts` / `engine.js parseWeeklyReports` | **Deterministic, no model.** Matches the labels of the two fixed templates SMK use (the headed Word report and the Microsoft Form printed to PDF). Text comes from mammoth / pdf.js in the browser; nothing leaves it. Several reports per file are fine. |
| images, or documents in any other layout | `/api/llm` via `extractDoc` (server: `ingest/extract.ts`) | A model reads it into rows. Needs a key; staff must check the result. Without a key the file fails with a message saying to use the SMK template or the Forms export. |

Both converge on `aggregateSubmissions()` in `src/lib/aggregate.ts`, then generation, then
`buildReport()` in `src/lib/report.ts`.

## Conventions

- **British English everywhere** — in the UI, the prompts and the generated reports.
- The **app chrome** is the warm SIEVEMK palette (espresso `#2A211B`, sand `#EFE4D3`,
  cream `#F2E9DC`, Cormorant Garamond + Jost). The **report document** is deliberately
  plain: black on white, Calibri (Carlito fallback), A4. Never mix the two.
- Derived ratings are heuristics over a form not designed for this report. They are always
  **editable** and labelled as derived. See `DERIVATION_NOTES` in `src/lib/aggregate.ts`.
- Default model is `claude-opus-5`. Responses use structured outputs
  (`client.messages.parse` + a Zod schema), never hand-rolled JSON parsing.
- Generation failures must **degrade, not break**: fall back to the template and tell staff
  in the toolbar why.

## Known problems — read before building on this

1. **A third of the repository is unreachable.** `src/components/` (9 files, 0 references),
   `artifact/` (the first design), and `/api/{upload,generate,export,regenerate}` with the
   `src/lib` modules only they import. The live UI fetches only `/api/llm`, `/api/pdf`,
   `/api/state`, `/api/reports`, `/api/settings`, `/api/health`, `/api/auth`. Deleting this
   removes a whole second copy of the report logic that otherwise has to be
   hand-synchronised with `artifact2/engine.js` on every change.

2. **`npm run check:privacy` validates code that does not run.** It imports
   `src/lib/pseudonymise.ts`; the app calls `E.pseudonymise` from `artifact2/engine.js`
   (`app.js`, in `buildReport`). Repoint the script at the engine before trusting it — and
   before deleting the TypeScript copy.

3. **`docs/reference/report-page-*.png` appear to be a real child's completed report**
   ("George Holmes, Spring 2026"), committed in the first commit and therefore in history.
   Confirm with SIEVEMK whether he is real. If so the images come out of history properly
   and prior commits are treated as exposed.

4. **Two front ends.** `artifact2/` is published both as a claude.ai artifact and served by
   Next. Every change needs publishing and testing twice. Once hosting is live the artifact
   should be frozen as a demo.

## Known gaps to raise with SIEVEMK

- The form captures no **Year/Key Stage**, **subject tier** or **average grade**. Staff type
  these into the setup panel per report. Adding them to the Form would remove that step.
- The term label is guessed from the dates and uses standard UK terms, but SIEVEMK's own
  sample calls 4 May – 11 June *"Spring Term"*. Staff can edit it; confirm their convention.
- `public/smk-logo.svg` is a **placeholder**. Get the real asset.
- Attendance comes from the weekly form, not a register.
